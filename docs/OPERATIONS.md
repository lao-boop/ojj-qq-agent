# 运行、配置与更新

## 运行位置

机器人运行在执行 `npm run start:wecom` 的机器上。GitHub保存源码，云端工作树用于开发，两者不会自动使Mac运行最新版。同一个Bot ID只运行一个实例。

在准备启动的目录确认：

```bash
pwd
node --version
git status --short --branch
git rev-parse HEAD
```

安装包目录可能没有 `.git`；此时以安装输出和 `work/upgrade-*/backup/release.json` 为版本依据。不要根据文件夹名称猜版本，也不要把实验目录当成正式运行目录。

## 配置与数据

- `.env`：密钥及平台环境变量。环境变量覆盖对应的配置字段。
- `config.json`：本机配置；首次启动按默认值/模板生成，控制台修改会保存。
- `data/`：人格、聊天、文件、秘书原话与进度；`QQBOT_DATA`可指定其他目录。
- `QQBOT_CONFIG`可指定配置文件。它不会把 `.env` 的搜索位置改到新目录；需要时显式加载该文件或设置进程环境变量。
- `work/upgrade-*/backup/`：安装器备份，可能包含配置，不能上传Git。

启用秘书时填写实际负责人UserID，默认间隔60分钟。需要白名单时分别配置成员UserID和群ChatID；白名单为空不放行。控制台监听本机，具体访问规则见[企业微信指南](WECOM.md)。

## 启动与停止

```bash
npm run start:wecom
```

前台运行时用Control+C停止。Mac睡眠、关机、断网会影响接收与按时发送；恢复后由持久状态继续处理。仓库尚未提供自动安装的系统服务或高可用部署方案。

## 更新已有运行目录

先停止机器人，记录当前版本并备份配置和数据。Git工作树有未提交修改时先审查保存，不用 `reset --hard` 覆盖本地工作；新克隆也不要覆盖原目录。

Git安装可在确认本地改动已妥善保存后用快进更新工作分支：

```bash
git fetch origin
git merge --ff-only origin/codex/wecom-integration
npm ci
npm run check:release
```

重新启动前核对模型、访问范围、秘书接收人及间隔。发布源码到工作分支不代表运行环境已安装，也不代表所有功能已通过生产验证。

历史固定提交更新入口：`node scripts/update-wecom.mjs <完整提交SHA> <负责人UserID>`。该入口会校验文件哈希、语法并备份，但保留了历史配置迁移规则，可能调整部分Office/出图默认配置。其清单只覆盖指定文件，不等同于全仓库同步。

专用本地发布包的 `scripts/install-wecom-mac.sh` 使用保留配置模式，逐字保留现有配置及聊天档案，不自动启动。GitHub源码压缩包不等于带发布清单的安装包；不要混用。回退应使用已记录的旧提交或对应备份，并检查配置/数据兼容性。

## 故障定位

| 现象 | 先检查 |
| --- | --- |
| Node提示缺少simdjson动态库 | Node本身不能启动；实验入口可使用独立官方Node24，不要通过改业务代码处理 |
| 企业微信CONNECT 403 | 代理/网络在认证前拒绝连接；换Bot Secret通常无效 |
| 能聊天但没有定时汇报 | 秘书开关、负责人ID、时间间隔、是否有其他成员新增消息、运行机器是否休眠 |
| 模型超时 | 查看哪个生成阶段失败；60秒是单请求预算，不是整个多批任务截止 |
| 更新提示文件校验失败 | 检查提交与清单是否匹配；开发者运行 `check:release`，不要跳过校验强装 |
| 已生成但未确认发送 | 保留outbox和档案，按原流程重试；ACK丢失可能重复投递 |

反馈时提供版本、阶段、匿名化原话与错误码。不要把 `.env`、完整用户配置或业务聊天档案贴到公开Issue。
