# 任务可靠性、入口隔离与记忆容量

工作分支为 `fix/architecture-routing-report`，不修改 main。本轮沿用单主 Agent＋受控工作流，补齐生产入口和任务生命周期；没有增加自主向外联系用户的功能。

## 群聊文件入口

`FileBatches` 使用会话和发送者共同作为合并键，保留文件、文字、@、引用等全部消息段。同一个人的连续文件仍会合并，不同成员不会共享待处理批次。自动注入的文件摘要和 `find_media` 也按发言人过滤；缺少发送人信息的旧群媒体索引不会自动归到某个成员。

## 记忆容量与失效来源

保存的便签不再被40条容量限制直接删除。模型上下文最多装入40条相关记录；相关性通过本地文本匹配计算，未加载的记录仍在磁盘，可用只读 `search_memory` 搜索或分页读取。模型明确知道上下文是否仅为部分记录，记录条数不代表事实项数。

临时记录到期时，会持久保存失效ID和来源请求，再移除有效便签；旧原文及派生回答继续被过滤，新增大量便签和重启不会撤销失效依据。聊天原始文件不做物理删除。当前实现仍是单进程拥有的JSON存储，适用于本项目部署方式，不支持多进程同时写同一数据目录；后续如需多实例，应迁移至带事务和并发控制的数据库。

## 任务状态与文件队列

生产入口把草稿、确认参数、排除项、请求人和任务状态写入 `data/tasks.json`。文档生成与上传的事实来自 `data/office-deliveries.json`，启动时校准任务状态。内存中的运行/排队任务在重启后先标为中断；文件队列中的待处理项改为暂停，等待用户明确继续。不会仅凭“重启成功”宣称任务完成。

文件队列一次执行一个任务。相同任务ID和相同完整作业参数再次进入队列时复用已有记录；同一任务中的不同文件仍分别保存状态。排队任务可以取消；正在生成或上传的工作目前不能可靠中止，也不会谎称取消成功。

继续分为两种情况：

- 尚未生成或生成中断：从生成阶段重新开始，保留原任务参数与已取得的参考资料，不重新执行其他业务工具。
- 文件已生成且尚未上传，或上传明确被拒绝/未发出：使用原文件继续上传，不再调用生成模型。

上传超时、断线或进程在发送中退出，结果标为未知，禁止自动重发，`/resume` 和 `/retry` 也不会把未知当作失败。已经发送的内容无法撤回。文件丢失时不偷偷重新生成。文档是本轮支持恢复的工作流；歌曲、翻唱、发图等其他副作用中断后只记录中断状态，不自动重做。

状态记录采用临时文件＋原子重命名。两个日志之间以交付日志为事实来源，启动时重新同步；这不是跨文件事务，也不保证断电场景下的严格事务持久性。任务列表最多显示最近12项；未完成任务不会因为时间或数量被直接淘汰。终态任务创建新任务时保留最近200项，文件交付记录目前不自动清理。

## 怎么使用

在已允许的QQ私聊或群聊中发送以下指令。群聊每位成员只管理自己的任务；这些指令直接读取状态，不经过模型，模型故障时仍可查询。

| 指令 | 行为 |
| --- | --- |
| `/tasks` 或 `我的任务` | 列出任务，显示8位编号 |
| `/task 编号` | 查询这项任务和各文件的实际状态 |
| `/cancel 编号` | 取消草稿或尚未执行的文件队列项 |
| `/resume 编号` | 继续可恢复的文件步骤；普通草稿仍需补齐需求并明确开始 |
| `/retry 编号` | 仅重发已明确上传失败的原文件 |

也支持 `/任务`、`/进度`、`/取消`、`/继续`、`/重发`。明确带编号的“查看任务 编号”“取消任务 编号”“继续任务 编号”“重发任务 编号”可直接处理。更自由的口语仍需要语义识别，不能据此承诺所有表达都绕过模型。

## 配置和耗时

新建配置默认 `chat.agents.enabled=true`、`architecture=single`，对话与Office默认 `deepseek-v4-pro`。已有配置中的明确覆盖仍保留，不会远程修改正在使用的QQ部署。`/status` 显示当前架构和文档模型。

```bash
node scripts/check_runtime_profile.mjs
```

该命令只读检查配置，不创建配置文件、不输出密钥，也不连接QQ。云端评测使用安全环境变量 `DEEPSEEK_API_KEY`；机器人运行仍读取自己的 `config.json`。评测成功不能代替生产部署检查。

每轮主Agent轨迹增加意图识别、执行模型和工具调用的分段耗时、结果及总耗时；去掉了重复装入的便签正文和完全相同的输入副本。没有放宽总执行预算，未承诺因此消除服务超时。对同一发言人的主对话处理串行，后台文件任务独立执行，直接任务指令不排在模型后面。

记忆工具现在接收本轮的 `m1`、`m2` 等短编号，由程序严格映射至当前用户真实记录；不对错误UUID做模糊猜测。存储层和来源屏蔽继续使用完整ID。模型若把工具名称和JSON直接写成正文，会得到一次格式修复机会，不会把这段正文当作工具命令执行。

草稿跨格式修改时，仅去掉前一格式不再适用的继承参数，例如PPT页数、Word节数或Excel行列数；本轮明确提出的冲突要求仍交由校验器说明。意图识别输入提供实际当前时间和用户时区，避免相对期限缺少日期依据。

## 验收

本地测试覆盖：多人交错附件、保留@和引用、111条长期记忆、过期来源不复活、草稿改口与取消持久化、任务日志损坏、排队取消、重启暂停、生成完成后的续传、明确失败后的原文件重发、重复恢复请求、未知回执不重发、成员边界、原文件丢失及同一任务多文件状态。

消息入口集成测试实际启动机器人子进程，以本地HTTP模型和本地OneBot WebSocket注入群消息，再停止并重启进程，验证文件归属、访问限制和状态恢复。没有连接真实QQ联系人。

真实模型使用提前固定的 `scripts/task-reliability-cases.mjs`：12个新场景、31轮输入，不复用此前21/24题及两批15题。部分场景预置48条便签用于测试存储容量，这不等同于48轮自然语言学习。真实Office生成和LibreOffice渲染继续使用生产实现，QQ回执仍为本地模拟。

```bash
node --test --test-concurrency=1 tests/*.test.js
node --use-env-proxy --use-system-ca scripts/evaluate_response_quality.mjs \
  --live --real-memory --suite=scripts/task-reliability-cases.mjs \
  --out=tmp/task-reliability-new-run
node scripts/response-quality-report.mjs tmp/task-reliability-new-run
```

本轮原始结果位于 `tmp/task-reliability-live`；新旧题不同，不能直接把两轮比例之差当作能力提升幅度。最终结果及逐题评分见同目录报告和 `tmp/task-reliability-summary.html`。

第一批完整结果为8/12达标、4项内容失败、0项服务异常。四项失败是工具名称作为正文、记忆UUID抄写错误、临时保存结构化输出连续截断，以及跨格式修改保留旧页数。结构化输出截断虽然传输请求成功，仍属于内容处理失败，不能当作服务超时剔除。

修复通用机制后，另行冻结 `scripts/task-reliability-reserve-cases.mjs` 的10个新场景、32轮输入，其中包括真实Office文件在模拟拒绝后用原文件重发，以及未知回执时拒绝重发。第二批没有复用第一批或之前题库的输入。原始结果在 `tmp/task-reliability-reserve`，第一批失败记录完整保留。

本地最终230项测试通过。另用 `scripts/compare_task_reliability.mjs` 对保留的修改前代码和当前代码执行相同的三项故障复现：群文件归属、过期记录在容量变化后不复活、草稿重启保留，均从失败变为通过。这是具体机制的前后验证，不是模型整体正确率提升的证明。

第二批最终10/10达到本轮标准，0项服务异常。真实生成4份文件、渲染4页，全部正文可从PDF提取，无空白页或越界文字，并完成逐页可视检查。明确失败后的重发复用了字节完全相同的原文件；结果未知的文件只有一次上传尝试。仍有少量人格闲聊、Excel打印表格偏小和Word末尾单字换行，达标不等于完美体验，也不能据此宣称真实QQ链路100%可靠。
